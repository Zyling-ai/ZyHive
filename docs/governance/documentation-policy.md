# ZyHive 文档政策

> 当前治理基线：`26.8.2v1`  
> 目标：让能力说明可追溯、状态可判断、版本可复核。

## 事实源与冲突处理

文档不是实现的替代品。关于“当前系统实际如何工作”的冲突按以下顺序裁决：

1. **当前版本代码与自动化测试**：代码定义可执行行为，测试定义已持续验证的行为；二者不一致时视为缺陷，不得只选择有利证据。
2. **同一版本的正式 Release**：公开 Release 资产、Release notes、发布门禁结果及 `CHANGELOG.md` 说明该版本实际交付了什么。已撤回、Draft 或失败候选不构成稳定事实。
3. **当前维护文档**：用户指南、管理员指南、开发者和参考文档解释已验证行为，但必须能回链到前两类证据。
4. **路线图、提案、审计快照、设计稿和演示记录**：只证明当时的目标、判断或实验结果，不证明当前实现。

代码存在但没有适当测试、默认产品路径或正式发布证据时，不得仅凭代码将能力标为 `Stable`。发现文档与高优先级事实源冲突时，应修正文档并记录影响版本；若代码和测试互相冲突，应先按缺陷处理。

## 状态标签

面向能力、页面、接口、配置或运维流程的文档必须使用以下标签之一。标签描述承诺程度，不描述完成百分比。

### Stable

同时满足：

- 位于当前正式版本的默认或明确支持路径；
- 有可定位的实现和自动化测试，关键用户路径还应有发布门禁或 E2E 证据；
- 前置条件、平台限制、失败模式和回滚方式已写明；
- 可以进入当前用户文档和发布承诺。

“需要 API Key、管理员配置或第三方服务”本身不使能力变成 Labs。缺少测试、仅有页面或路由、仅在开发环境运行过，都不足以标记 Stable。

### Labs

已存在可运行实现，但满足任一情况：默认关闭、通过 `EXPERIMENTAL` 开关启用、接口/数据格式可能破坏性变化、验证范围不足，或明确不进入稳定商业承诺。

Labs 文档必须写明开关、依赖、数据隔离、已知风险、停用/回滚方法和“不用于高风险决策”的边界。Labs 不得在无标签的用户主路径中被描述为默认能力。

### Planned

仅处于路线图、提案或设计阶段，或尚未达到可用条件。必须使用将来时并声明没有发布日期和交付承诺；不得提供看似当前可执行的安装、API 或操作步骤。实现合并后也不能自动转为 Stable，需重新按 Stable/Labs 条件评估。

### Accepted Risk

已知、经明确决定暂不消除的当前风险或产品边界。必须写清：

- 风险场景与影响；
- 接受范围和责任主体；
- 部署者必须采取的缓解措施；
- 重新评审触发条件。

Accepted Risk 不是“已修复”、不是“低风险”，也不替代安全告警。风险消除或范围变化时，应同步更新安全文档、功能状态和发布说明。

## 文档更新责任

文档更新是功能完成条件的一部分，不是发布后的可选清理。

- **变更作者**：识别受影响的用户流程、API、CLI、配置、部署、安全和状态标签，在同一变更中更新文档与覆盖矩阵。
- **代码审阅者**：核对文档是否引用了正确实现与测试，标签是否符合定义，示例是否可执行，是否误把历史材料当成当前事实。
- **模块维护者**：对模块入口、默认值、兼容性、风险和弃用说明负责；跨模块变更由发起变更的维护者协调。
- **发布负责人**：在公开 Release 前核对版本、`CHANGELOG.md`、安装/升级/回滚、平台资产和发布门禁，阻止带有错误版本或过期证据的文档发布。
- **安全相关变更负责人**：同步更新威胁边界、密钥/Token 处理、网络暴露、权限、审计和 Accepted Risk；不能只更新通用用户指南。

如果紧急修复无法同时完成文档，变更记录必须列出缺口、责任人和最晚补齐版本；涉及安全、数据损坏、迁移或公开 API 的缺口不得延期到发布后。

## 版本规则

- 当前版本以正式 Git Tag/Release 和构建时注入版本为准；`CHANGELOG.md` 记录版本语义，文档不得自行创造版本号。
- 只在行为与特定版本强绑定时固定写版本号；长期指南优先写“当前正式版”，并链接版本事实源。
- 固定版本页面必须在页首声明适用版本或版本范围。复制到新版本前必须重新验证，不能只替换字符串。
- 已撤回、Draft、预发布和历史版本必须显著标注，不能称为“最新版”或稳定基线。
- 命令参数、默认值、API 路径和环境变量应从对应版本二进制 `--help`、路由、schema 或测试核对。

## 截图规则

- 截图必须来自所声明版本和支持的平台，裁掉 Token、API Key、个人信息、内部域名和客户数据。
- 截图附近记录版本、页面路由、平台及必要的实验标签；Labs 页面必须在图注中标记 Labs。
- UI 文案、导航、权限、关键交互或状态发生变化时，相关截图必须重拍。仅视觉装饰变化可由审阅者判断是否重拍。
- 截图不能作为唯一操作说明；关键步骤和错误处理必须有可搜索文本。
- 无法确认来源版本的截图按历史材料处理，不得进入当前安装、安全或操作指南。

## 图表与生成内容规则

- Mermaid、架构图、路由表、API 表和统计图必须记录源数据或生成脚本、生成命令、生成日期及适用版本。
- 可由代码生成的内容不得手工维护第二份权威副本；生成结果应能在干净环境中重复得到。
- 路由、模块依赖、数据格式、发布流程或指标来源变化时，应重新生成并审阅语义，不得只更新图片文件。
- 没有生成来源的旧图表按历史示意图处理，并明确“非当前拓扑/非当前指标”。
- 图表中的数量、覆盖率和性能值必须附测试条件；不得把一次测试结果描述为持续保证。

## 合并与发布检查

- 状态标签符合本政策，且没有用 Planned/Labs 内容暗示 Stable。
- 用户可见行为有当前代码和测试证据；Release 承诺有正式发布证据。
- 覆盖矩阵的入口、证据、负责人或缺口已同步。
- 新增配置、CLI、路由和安全边界已进入对应参考文档。
- 版本、链接、命令、截图、图表和示例均已复核。
- 历史资料保留原始语境并带有“不代表当前实现”的警告。
