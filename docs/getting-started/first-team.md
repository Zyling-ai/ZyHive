# 创建第一个团队

> 前提：已按[安装说明](installation.md)启动 ZyHive，并持有管理员 Token。

本教程完成一个最小但真实的两成员团队：主助手负责接收任务，研究助手负责整理资料。先只使用管理界面对话，不配置外部渠道和高风险工具。

## 1. 登录并确认版本

1. 打开安装器输出的访问地址；
2. 输入管理员 Token；
3. 在终端运行 `zyhive --version`，确认版本为当前安装的正式 Release；
4. 如果需要重新查看 Token，在私密终端运行 `zyhive token`。

`zyhive token` 输出明文，不要在共享屏幕或终端日志中使用。

## 2. 配置 Provider 和模型

打开“模型”配置页：

1. 在“已配置厂商”中点击“添加”；
2. 选择 Provider，填写名称和 API Key；
3. 只有在使用自定义兼容服务或本机 Ollama 时才填写自定义服务地址；
4. 点击“保存并测试”，确认状态有效；
5. 选中该 Provider，点击“获取可用模型”；
6. 选择一个支持工具调用的模型并添加。

实例中的第一个模型会成为默认模型。模型列表探测依赖 Provider 实际接口；如果 Provider 不支持列举模型，可通过当前界面允许的方式添加明确的模型标识，不要猜测不存在的模型名。

完成标准：

- Provider 测试成功；
- 至少有一个 Model；
- Model 关联正确的 Provider；
- 计划使用工具时，模型没有“无工具”标记。

## 3. 检查初始成员

首次启动会创建：

- `main`：显示名“主助手”的普通成员；
- `__config__`：内置系统配置助手，不作为业务成员使用。

打开“成员”，进入 `main`。为它补充：

**IDENTITY**

```text
你是团队主助手。负责理解用户目标、拆分任务、判断何时需要其他成员，并整合最终答复。
```

**SOUL**

```text
先澄清事实，再给结论。表达简洁；不确定时明确说明，不虚构执行结果。
```

将 `main` 绑定到刚才配置的模型并保存。

## 4. 创建研究助手

在“成员”页面点击新建，填写：

- 名称：`研究助手`
- ID：`researcher`
- 描述：`负责检索、整理和核对资料`
- 模型：选择已验证的模型

填写：

**IDENTITY**

```text
你是研究助手。负责收集、比较和整理资料，区分事实、推断和未知项，并把可复核的结果交给主助手。
```

**SOUL**

```text
保守、可追溯。没有证据时不下确定结论；输出先给摘要，再列关键依据和待确认项。
```

暂时不要添加 Telegram、公开 Web 渠道或执行类工具。点击“保存 Agent”。

创建流程会写入 `IDENTITY.md`、`SOUL.md`，并尝试为成员开启每日自动记忆；如果附加配置失败，成员本身仍可能已创建，应进入成员详情复核，而不是重复点击创建。

## 5. 建立协作关系

打开“通讯录/团队”中的 AI 成员网络：

1. 在 `main` 与 `researcher` 之间建立允许协作的关系；
2. 保存后刷新图谱，确认两者已连接。

普通成员派遣目标成员时必须有关系连接。没有关系时，不应把派遣失败误判为模型故障。

## 6. 从最小权限开始

进入全局工具策略和两个成员的工具权限：

1. 全局只开放当前测试需要的能力；
2. `main` 保留对话和成员派遣所需能力；
3. `researcher` 暂不开放命令执行、外部消息发送或文件删除；
4. 对有副作用但偶尔需要的工具使用 `ask`；
5. 保存后查看成员“工具体检”，确认工具是 ready 还是 blocked。

成员策略不能突破全局上限。`ask` 无法连接审批中心时会拒绝执行，这是安全行为。

## 7. 验证单成员对话

回到首页，选择 `researcher`，发送：

```text
请把“事实、推断、未知项”三者的区别整理成一个简短检查清单。不要使用外部工具。
```

确认：

- 回复以流式方式出现并最终结束；
- 刷新页面后会话仍在；
- 历史会话中可以重新打开；
- 用量页面出现对应记录（费用仅为估算）。

如果失败，先检查 Provider 状态、成员绑定模型和服务日志，不要立即开放更多工具。

## 8. 验证团队协作

选择 `main`，发送：

```text
请让研究助手整理一份“上线前事实核对清单”，然后你把它压缩成 5 条最终建议。不要调用外部网络或命令工具。
```

观察派遣任务状态，并确认研究助手结果回传给 `main`。若模型没有选择派遣，可明确补充“必须派遣 researcher 完成资料整理”；LLM 是否自主调用工具仍受模型能力、提示和策略影响。

成功标准：

- 派遣未被关系或工具策略拒绝；
- 后台任务有明确终态；
- `main` 的最终回答区分了子任务结果与自身整合；
- 工具审计中可以找到对应调用。

## 9. 建立共享项目

打开“项目”，新建：

- ID：`team-handbook`
- 名称：`团队手册`
- 描述：`存放团队共同维护的规范与检查清单`

按界面为 `main` 和 `researcher` 配置所需读写权限，再创建一份简单说明文件。共享项目适合团队知识；成员私有草稿应保留在各自工作区。

## 10. 完成后的安全检查

- [ ] 管理员 Token 未进入聊天、截图或版本库；
- [ ] Provider 与 Model 均已真实测试；
- [ ] 两个成员的职责和行为边界已写入身份文件；
- [ ] 协作关系已建立；
- [ ] 工具权限遵循最小权限；
- [ ] 单成员对话、历史会话和团队派遣均已验证；
- [ ] 已创建第一次备份，并计划隔离恢复演练。

接下来可按需求逐项启用 Cron、Telegram、飞书或公开 Web 聊天。每增加一个外部入口，都应重新检查身份、速率、数据暴露和工具权限。aiteam 与 SkillOpt 属于 Labs，不应作为首次团队搭建的必选步骤。
